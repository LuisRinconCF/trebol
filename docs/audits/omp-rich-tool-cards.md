# Oh My Pi rich tool cards vs Pi-Swarm

## Purpose and scope

Compare the *visual UI patterns* of Oh My Pi (OMP) tool cards—not model-facing schemas—with corresponding Pi-Swarm tool renderers. User requested each tool, concrete UI examples, and improvements. Findings below are source inspection, not live TUI/browser verification.

OMP baseline is vendored revision `daf07999c2fee9b22edc7bf8fea1fb6272e0df5e` (`vendor/oh-my-pi/packages/coding-agent/src/tools/renderers.ts`). Its registry has these renderer families: Ask; AST Grep/Edit; Bash; Debug; Eval; Edit/Apply Patch; Glob; Grep; LSP; Hub; Read; Resolve/Reject; Retain/Recall/Reflect; Task; Think; Todo; GitHub; Goal; Web Search; Vibe spawn/send/wait/kill/list; Write. Registrations: `vendor/oh-my-pi/packages/coding-agent/src/tools/renderers.ts#L95-L141`.

Pi-Swarm scope follows active layer manifests, especially `.pi/extensions/30-tools/package.json`, `.pi/extensions/10-context/package.json`, and `.pi/extensions/40-state/package.json`, plus runtime bootstrap. Custom tools may be added dynamically (MCP), so the audit groups by renderer pattern and notes non-equivalence. Pi-Swarm source reveals dedicated `renderCall`/`renderResult` implementations for foreground/background Bash, ask-user, history-search, TaskManage and Bootstrap. Other registered tools mostly get the shared default result renderer, or have no explicit tool renderer.

## Baseline and verification limits

OMP source contract: `vendor/oh-my-pi/docs/tui.md` describes interactive TUI, headless and RPC modes; tool renderers receive call/result state and theme. It emphasizes component stability, semantic theme usage, and rich custom components. Specific renderer examples below come from source paths; they are not screenshots. I did not launch OMP or Pi-Swarm in an interactive TUI, exercise actual tool calls, capture matched themes/viewports, or validate live keyboard/overlay behavior. Therefore “OMP does X” below means source implementation indicates it, not that a live session was observed.

## What makes OMP cards feel rich

- **Action-first status line:** common renderer helper `renderStatusLine` composes status icon, tool title, concise action description and optional metadata. E.g. Read shows path/line range; Grep shows query; Glob shows target; Write shows language/path. (Read `.../tools/read-renderer.ts#L83-L104`; Grep `.../tools/grep.ts#L1809-L1825`; Glob `.../tools/glob.ts#L609-L627`; Write `.../tools/write.ts#L1600-L1655`.)
- **Result is a mini-report, not a dump:** renderers produce framed blocks, tree/file lists, code cells, diff views, badges, hyperlinks, counts and truncation/expand hints. Examples: Grep and Glob render grouped tree rows; Read renders code/markdown cells; Edit and Write render diff/operation summaries.
- **State-specific visual language:** pending/running/success/warning/error icons and theme-defined symbols/colors; special timeout/partial/truncated/no-result states. Bash result differentiates success, partial, error and timeout (`.../tools/bash.ts#L1686-L1717`).
- **The tool card understands its domain:** GitHub groups operation status, Web Search displays provider and source tree, Task visualizes nested agent progress, Todo renders task tree, Vibe explains session lifecycle, memory tools format retained/recalled knowledge.
- **Collapse is deliberate:** tool-specific preview limits and expansion hints preserve the important header/action context rather than treating all output identically. Some renderers merge call and result; registry exposes `mergeCallAndResult`, animation and activity-summary hints (`.../tools/renderers.ts#L57-L93`).
- **Custom UI when a card is not enough:** OMP extension UI can replace the editor area or mount a focused overlay and restore editor state on completion (`vendor/oh-my-pi/docs/tui.md#L96-L120` onward). This is separate from transcript tool cards.

## Pi-Swarm rich-card inventory (source scan)

- Dedicated custom cards found: `bash` (`.pi/extensions/30-tools/swarm-bash.ts#L42-L51`); background Bash (`swarm-background-bash.ts#L68-L84`); `ask_user_question` (`ask-user/index.ts#L2372-L2390`); `history_search` (`history-search.ts` renderer at line 164); TaskManage (`packages/tools/taskmanage/src/task-manage.ts#L308-L343`); Bootstrap (`.pi/lib/ui/bootstrap-tool-renderer.ts#L151-L165`).
- Shared generic result adapter: `packages/runtime/core/src/tool-renderer.ts#L47-L68`; generic adapter does not create tool-specific call cards.
- Active tools manifest identifies filesystem, research, control-task, agent, history, ask, Bash, MCP, schedule, task, vault and code-mode registrations: `.pi/extensions/30-tools/package.json`.
- There are tools registered outside `30-tools` (e.g. skills/context/bootstrap/runtime) and runtime-discovered MCP tools. “Each” therefore means every family identified in active manifests/source scan, not every possible dynamically discovered remote MCP tool.

## Adoption priorities (recommendations, not observed facts)

1. **Read and file mutations first.** OMP’s path-aware Read and diff-aware Edit/Write cards make a common journey scannable. Add summaries for Pi-Swarm `Read`, `apply_patch`, and `Undo`: status + shortened path + lines/files changed + bounded preview + explicit failure. Acceptance: representative text/image reads and single/multi-file patches show useful collapsed summary; expansion reveals full bounded details; permission/error states remain unmistakable.
2. **Search and web results next.** Borrow OMP’s grouped tree/source cards for local search and web search/fetch. Acceptance: query/provider visible; grouped result count and source/title/snippet visible; empty/error/truncated results distinct; links and expanded details work.
3. **Agent lifecycle cards.** Make `Agent`, `AgentControl`, `ReadBackgroundCommand` tell a coherent spawn→running→complete/fail/cancel story, with summary and status rather than generic JSON. Acceptance: asynchronous states visibly differ and controls’ outcome is clear without placing TUI-only progress into model context.
4. **TaskManage parity polish only if it adds information.** It already has status icons, question rows, error styling and width-aware results. Compare live with OMP Todo/task first; only add hierarchy/aggregate counts if users can scan task trees better.
5. **Leave `think` alone; avoid blanket carding of every one-off tool.** OMP Think intentionally renders nothing. Keep Bootstrap specialized and preserve redaction/evidence. Build high-quality patterns around common workflows rather than styling every generic result just for symmetry.
